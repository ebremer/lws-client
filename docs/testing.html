Testing & mock server

Seven independent implementations only stay consistent if they are tested against the same data. The repository has three layers of shared testing: conformance fixtures, a mock LWS server, and an end-to-end interop scenario.

Conformance fixtures

conformance/fixtures/ holds language-neutral JSON test vectors. Every client's unit tests load them directly, so a parsing bug fixed in one language is caught in all seven.

FixtureCovers
link-headers.jsonRFC 8288 Link parsing: quoting, commas inside URIs, multiple relation types, relative targets
www-authenticate.jsonChallenge parsing including several challenges in one header and token68
structured-fields.jsonRFC 8941/9651 dictionaries used by Signature-Input, Signature and Content-Digest
json-patch.jsonJSON Pointer escaping and JSON Patch serialisation
type-queries.jsonapplication/lws-query+json construction and client-side validation
did-key.jsondid:key derivation, including the official did:key P-256 test vector
jwt.jsonSelf-signed ES256 and EdDSA credentials that every client must verify
webhook/*.json13 RFC 9421 signed deliveries: 3 valid and 10 attacks (tampered body, recomputed digest, wrong host, replay, missing components, unauthorised key, storage spoofing, algorithm confusion, …)
responses/*.jsonReal-shaped HTTP responses (storage description, paginated container with relative ids, linkset, notifications, access documents, OAuth metadata, problem details) with the expected parsed models

The cryptographic fixtures are generated by a committed script (keys are reused, signatures are re-randomised):

node conformance/tools/generate-fixtures.mjs

Mock LWS server

testing/mock-server is a zero-dependency Node.js (20+) implementation of the server side of every spec the clients cover. It is an in-memory storage with real authorization (token exchange, signed access tokens), pagination, linksets, JSON Patch, signed webhooks, access request and grant containers, and type index and search over HTTP QUERY.

node testing/mock-server/server.mjs --port 8787
# LWS mock server listening on http://localhost:8787
OptionDefaultMeaning
--port <n>8787Listen port (0 picks a free port)
--host <addr>IPv4 + IPv6 loopbackInterface to bind
--base-url <url>http://localhost:<port>Public origin used in every URL the server emits
--page-size <n>5Page size for containers, the type index and search results (small, so pagination is always exercised)
--no-authoffDisable authentication; every request acts as anonymous
--verboseoffLog requests, token exchanges and webhook deliveries

Node.js 22 or newer is recommended: the server relies on Node's HTTP parser accepting the QUERY method. It can also be started from code with startServer({ port: 0 }) from testing/mock-server/lib/server.mjs, which resolves to { url, close() }.

URLPurpose
{base}/Storage description (public)
{base}/root/Storage root container
{base}/notifications/Notification service (WebhookSubscription)
{base}/access/requests/, {base}/access/grants/Access request and grant services
{base}/types/index, {base}/types/searchType index and type search services
{base}/.well-known/lws-configurationAuthorization server metadata (issuer {base})
{base}/oauth/token, {base}/oauth/jwksToken exchange endpoint and signing keys

Test use only The mock server keeps everything in memory, grants every authenticated agent full access and accepts unverified OpenID/SAML tokens in test mode. Never expose it to a network.

Interop scenario

conformance/scenario.md defines one end-to-end scenario that every client runs against the mock server. It covers self-signed did:key authentication through the full 401 → token exchange flow, discovery, CRUD with conditional requests, JSON Patch, linkset patches, pagination across pages, type index and search, signed webhook delivery and verification, access requests and grants, and recursive delete. Each language gates the test on LWS_TEST_SERVER:

node testing/mock-server/server.mjs --port 8787 &
export LWS_TEST_SERVER=http://localhost:8787

(cd java && mvn -q verify)
(cd js && npm run test:interop)
(cd cpp && ctest --preset debug)            # or: ctest --test-dir build/mingw-debug
(cd rust && cargo test --test interop)
(cd go && go test -run TestInterop -v .)
(cd python && .venv/bin/pytest tests/test_interop.py)   # Windows: .venv\Scripts\pytest
(cd csharp && dotnet test)

Running each test suite

Unit tests need no server. See each language's build commands. Every suite includes in-process HTTP tests that simulate an LWS server, including the authorization flow, realm-check rejection, three-page pagination, 304/412 handling and error mapping.
