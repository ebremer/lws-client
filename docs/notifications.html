Notifications & webhooks

A storage that advertises a NotificationService can POST change notifications to an inbox you control. The clients manage subscriptions, and verify each delivery's signature against the key the storage publishes before you act on it.

Managing subscriptions

A subscription names one or more topic resources and an inbox URL. Subscribing to a container is recursive: you receive events for everything below it that you are allowed to read, both when you subscribe and when each event is delivered. The service's subscriptionType must include WebhookSubscription. The storage-description overloads check this for you.

The notification model

{
  "@context": ["https://www.w3.org/ns/lws/v1", "https://www.w3.org/ns/activitystreams"],
  "type": "Notification",
  "storage": "https://storage.example/",
  "activity": [{
    "id": "urn:uuid:a1b2c3d4-…",
    "type": ["Create"],
    "object": { "id": "https://storage.example/root/notes/meeting.txt", "type": ["DataResource"] },
    "target": "https://storage.example/root/notes/",
    "published": "2026-09-21T11:33:20Z"
  }]
}
FieldMeaning
storageThe storage the events belong to (checked against the signing key)
activitiesAlways a list, even when the server sent a single object (servers may batch)
typesCreate, Update (content or metadata) or Delete; helpers isCreate(), isUpdate(), isDelete()
objectThe resource's id and types
target / originContainer a resource was added to (Create) or removed from (Delete)
actor, publishedWho acted (optional) and when

parseNotification parses a body you have already verified, or trust for another reason.

Receiving and verifying deliveries

Anyone can POST to your inbox, so verify every delivery before you trust it. The verifier is framework-agnostic: it takes the method, the registered inbox URL, the headers and the raw body bytes. Most languages also ship a small adapter for their standard server:

LanguageAdapter
JavaHttpExchangeWebhooks.verify(verifier, exchange, inbox) for com.sun.net.httpserver (optional module)
TypeScriptverifier.verify(request) for Fetch Requests; createWebhookHandler from lws-client/node for node:http
C++verifier.verify(method, url, headers, body), callable from any server
Rustverify_request(&inbox, &http::Request) for any http-based framework
Goverifier.Handler(inbox, fn) as an http.Handler, or VerifyRequest(r, inbox)
PythonWebhookVerifier.verify(…); AsyncWebhookVerifier.verify_asgi(scope, receive, inbox) for ASGI
C#verifier.VerifyAsync(context.Request, inbox) for System.Net.HttpListener; ASP.NET Core and others pass the method, inbox, HeaderMap.From(…) and body
Swiftverifier.verify(method:url:headers:body:), callable from any server (Vapor, Hummingbird, SwiftNIO…)
PHP$verifier->verifyGlobals($inbox) in a plain PHP script, verifyServerRequest($request, $inbox) for PSR-7, or verify(…) with the parts
import com.ebremer.lws.LwsClient;
import com.ebremer.lws.SignatureVerificationException;
import com.ebremer.lws.notify.HttpExchangeWebhooks;
import com.ebremer.lws.notify.Notification;
import com.ebremer.lws.notify.VerifiedNotification;
import com.ebremer.lws.notify.WebhookVerifier;
import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.net.URI;
import java.util.List;

public class Inbox {
    public static void main(String[] args) throws Exception {
        WebhookVerifier verifier = WebhookVerifier.builder()
                .client(LwsClient.create())                                         // fetches storage descriptions
                .trustedStorages(List.of(URI.create("https://storage.example/")))  // only this storage's keys
                .build();
        URI inbox = URI.create("https://my-app.example/hooks/lws");  // the registered (public) URL

        HttpServer server = HttpServer.create(new InetSocketAddress(8080), 0);
        server.createContext("/hooks/lws", exchange -> {
            try {
                VerifiedNotification verified = HttpExchangeWebhooks.verify(verifier, exchange, inbox);
                for (Notification.Activity a : verified.notification().activities()) {
                    System.out.println(a.types() + " " + a.object().id() + " " + a.published());
                }
                exchange.sendResponseHeaders(204, -1);
            } catch (SignatureVerificationException e) {
                exchange.sendResponseHeaders(401, -1);
            } finally {
                exchange.close();
            }
        });
        server.start();
        // Other frameworks: verifier.verify(method, inbox, headers, body)
    }
}

// Call from your HTTP server (Boost.Beast, Drogon, cpp-httplib, …) with the raw request.
int handle_delivery(lws::WebhookVerifier& verifier, std::string_view method,
                    const lws::HttpHeaders& headers, std::string_view body) {
    // The URL you registered (your public URL when behind a proxy), not the Host header.
    constexpr std::string_view inbox = "https://my-app.example/hooks/lws";
    try {
        lws::VerifiedNotification verified = verifier.verify(method, inbox, headers, body);
        for (const lws::Activity& a : verified.notification.activities) {
            std::cout << a.object.id << (a.is_update() ? " updated" : "") << '\n';
        }
        return 204;
    } catch (const lws::SignatureVerificationError& e) {
        std::cerr << "rejected: " << e.what() << '\n';
        return 401;
    }
}

use lws_client::{Client, Result, Url, WebhookVerifier};

/// Builds a verifier that only accepts deliveries signed by one storage.
fn verifier() -> WebhookVerifier {
    let storage = Url::parse("https://storage.example/").expect("valid URL");
    WebhookVerifier::builder()
        .client(Client::new())        // fetches storage descriptions (and their keys)
        .trusted_storage(storage)     // only this storage's signatures
        .build()
}

/// Call this from your web framework's handler with the raw request; returns the status to send.
async fn handle(verifier: &WebhookVerifier, request: http::Request<Vec<u8>>) -> Result<u16> {
    // The URL you registered (your public URL when behind a proxy), not the Host header.
    let inbox = Url::parse("https://my-app.example/hooks/lws").expect("valid URL");
    match verifier.verify_request(&inbox, &request).await {
        Ok(verified) => {
            for a in &verified.notification.activities {
                println!("{:?} {} {:?}", a.types, a.object.id, a.published);
            }
            Ok(204)
        }
        Err(e) if e.is_signature_verification() => Ok(401),
        Err(e) => Err(e),
    }
}

Use the URL you registered Verify against the inbox URL you gave the storage, not one rebuilt from the Host header. Behind a reverse proxy, that is your public URL. The signature covers @scheme, @authority and @path, and this is what stops a delivery meant for someone else from being replayed at you.

What the verifier checks

  1. Content-Digest (RFC 9530) matches the body: every sha-256/sha-512 value present must match.
  2. Signature-Input covers at least @method, @scheme, @authority, @path, content-type and content-digest, and carries created and keyid.
  3. created is within the allowed window (default 300 s either way), and expires, if present, has not passed.
  4. The keyid is a URL with a fragment. Without the fragment it names the storage, which must be in trustedStorages when you set it.
  5. The storage description is fetched (and cached). Its id must equal that storage, the verification method must exist, and it must be referenced from authentication.
  6. The RFC 9421 signature base is rebuilt and verified with the published JWK (ecdsa-p256-sha256 or ed25519). A matching alg parameter is required when present. On failure with a cached key, the description is fetched once more to handle key rotation.
  7. The body is parsed, and its storage must equal the signing key's storage, so one storage cannot speak for another.

All nine verifiers pass the same 13 shared test vectors. They include tampered bodies, recomputed digests, wrong hosts, replays, missing components, unauthorised keys, storage spoofing and algorithm confusion.

Delivery semantics

  • Answer with any 2xx to acknowledge. Servers may retry failed deliveries and deactivate a subscription after repeated failures.
  • Retries can deliver the same activity twice, so de-duplicate on the activity id.
  • Use a unique, hard-to-guess inbox URL per subscription. It limits correlation, and lets you revoke a single feed.
