Type index & search

Instead of crawling containers, ask the storage which types exist with the TypeIndexService. Then find the matching resources with the TypeSearchService, which takes a conjunctive-normal-form filter sent with the HTTP QUERY method.

Listing types

listTypes pages through the type index lazily. Types come from rel="type" links you set when creating or updating resources, plus the intrinsic LWS classes. They are filtered to what you are allowed to read.

storage.typeIndexService().ifPresent(index ->
        client.listTypes(index.serviceEndpoint()).forEach(System.out::println));  // e.g. https://schema.org/Person
const index = storage.typeIndexService();
if (index) {
  for await (const type of client.listTypes(index)) console.log(type);  // e.g. https://schema.org/Person
}
if (const lws::Service* index = storage.type_index_service()) {
    for (const std::string& type : client.list_types(index->service_endpoint)) {
        std::cout << type << '\n';   // e.g. https://schema.org/Person

Searching by type

A filter is a list of AND-ed groups, where each group is one IRI or an OR-list of IRIs. The builders produce exactly that:

Builder callSerialised filterMeaning
allOf(A, B){"type": ["A", "B"]}A AND B
anyOf(A, B){"type": [["A", "B"]]}A OR B
anyOf(A, B) then allOf(C){"type": [["A", "B"], "C"]}(A OR B) AND C
relation("describedby").allOf(S){"describedby": ["S"]}has a describedby link to S
(nothing){}every resource you can see
URI search = storage.typeSearchService().orElseThrow().serviceEndpoint();

// (schema:Person OR foaf:Person) AND lws:DataResource
TypeQuery query = TypeQuery.builder()
        .anyOf("https://schema.org/Person", "http://xmlns.com/foaf/0.1/Person")
        .allOf(Lws.Type.DATA_RESOURCE)
        .build();
ContainerPage first = client.searchTypes(search, query);         // HTTP QUERY
System.out.println(first.totalItems() + " " + first.next());

client.searchAll(search, TypeQuery.allOf("https://schema.org/Event"))
        .forEach(hit -> System.out.println(hit.id() + " " + hit.types()));

// Indexed descriptive relations use the same grammar.
TypeQuery shaped = TypeQuery.builder().relationAllOf("describedby", "https://example.org/shapes/person").build();
System.out.println(client.searchTypes(search, shaped).items().size());

System.out.println(client.acceptedQueryFormats(search));        // [application/lws-query+json, …]

The first page comes from QUERY. Later pages are opaque links fetched with GET. searchAll handles both for you. Results use the container page shape, but they are a synthetic, per-client result set, not a container.

Rules and errors

  • Every value must be an absolute IRI, and empty OR-groups are invalid. The client builders reject both before sending, because the server would answer 400.
  • An unknown type, or a relation the server does not index, simply matches nothing. It is never an error, and servers never reveal which relations they index.
  • Overly complex filters get 422, unsupported query formats get 415 (see acceptedQueryFormats), and expired page links get 404/410. In that last case, restart the search.
  • Type derivation may be eventually consistent, so a resource you just created can take a moment to show up. Authorization filtering, however, is always current.

Make resources findable Servers are not required to parse resource bodies. Declare types with types (extra rel="type" links) when you create a resource, or add them to its linkset later.
